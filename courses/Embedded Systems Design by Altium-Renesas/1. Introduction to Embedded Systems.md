> [!abstract] Key idea
> An **embedded system** is a computer built into a larger product to do **one dedicated job**. It's defined by its **constraints** (real-time deadlines, power, reliability, cost and size), not by raw computing power.

- An embedded system is a **purpose-built computer**: hardware and software designed together for **one dedicated function**.
- It's a **system within a system**, a part inside a larger mechanical or electrical product. That's why it's called *embedded*.
- Examples: the controller in a microwave, the GPS module in a phone, the **engine control unit (ECU)** in a car.
- A microwave controller can only run the timer and the heater. This **task specificity** is what separates it from a general-purpose laptop.

### 0.1.1 Two Examples
| | Digital watch | Industrial robotic arm |
|---|---|---|
| **Function** | Clock, stopwatch and alarms | Precise, repetitive tasks on an assembly line |
| **Inputs** | Button presses: mode, start/stop, set | Commands from a central controller, plus **joint sensor** positions |
| **Processing** | A microcontroller runs the timekeeping software | A control unit compares the commands with the sensor feedback and calculates each movement |
| **Outputs** | LCD digits and symbols, beeper | Signals to the **motors (actuators)**, plus status back to the controller |

- The robotic arm is a **closed loop**. Its sensors report where each joint really is, and the control unit keeps correcting the motor commands.

### 0.1.2 General Structure
- A **microcontroller** sits at the heart and controls everything.
- Inputs and outputs, such as sensors, displays and actuators, connect directly or through **driver circuits**. A driver circuit is needed because an MCU pin can't supply the current a motor or relay needs.
- Extra parts are added **only when the application needs them**: memory, communication modules such as Wi-Fi and Bluetooth, and power management.
- The result is **custom-built for one task**, which makes it reliable, compact and efficient.

## 0.2 Embedded vs General-Purpose Computers
| Characteristic | Embedded system | General-purpose computer |
|---|---|---|
| **Purpose** | Dedicated, single function | Versatile, multitasking |
| **Resources** | Constrained, often **KBs of RAM** | Abundant, GBs of RAM |
| **Power** | Low consumption is critical | High consumption is fine |
| **Cost** | Low per-unit cost is critical | High per unit |
| **User interface** | Minimal or none, such as LEDs and buttons | Rich: a GUI, keyboard and screen |
| **Reliability** | Must be high, because a failure can be dangerous | A crash is an inconvenience |

## 0.3 Defining Characteristics
### 0.3.1 Real-Time Operation
> [!abstract] Real-time doesn't mean fast
> **Real-time** means **predictable and deterministic**: the correct result arrives **before its deadline, every time**. A slow system that always meets its deadline is real-time, and a fast one that sometimes misses it isn't.

- **Hard real-time:** missing a deadline is a **catastrophic failure**. Examples are airbag deployment, anti-lock brakes (ABS) and a flight controller.
- **Soft real-time:** missing a deadline **degrades performance** but isn't catastrophic. Examples are live video streaming, an ATM transaction and a smart home device responding.

### 0.3.2 Efficiency and Low Power
- Low power is critical for **battery-powered** devices such as wearables and IoT sensors.
- Less power also means **less heat**, which allows small, **fanless** designs.
- It's achieved with **sleep modes**, optimized code and low-power components.

### 0.3.3 Reliability
- An embedded system must run **flawlessly for years** with no one looking after it.
- In **safety-critical** systems, failure isn't an option: pacemakers, satellite controllers and industrial safety systems.

### 0.3.4 Cost and Size
- **Per-unit cost** drives the design. Saving a fraction of a cent matters when you build millions of units.
- Cost pressure pushes parts onto **a single chip**, a **System on Chip (SoC)**.
- **Size** is often a hard limit: smart rings, hearing aids and small sensors.

## 0.4 Hardware Anatomy
Every embedded system is built from three hardware blocks:
- the **processing unit**, which is the brain
- the **memory**, which holds the code and working data
- the **input/output peripherals**, which are the senses and muscles that link the system to the physical world.

> [!info] The real MCU and MPU dividing line
> Modern MPUs, such as the RZ family, have plenty of on-chip peripherals too. The practical difference is that an **MPU usually runs from external DRAM** and has a **memory management unit (MMU)**, so it can run Linux. An **MCU runs from its own flash and SRAM**, usually bare-metal or with a small RTOS. Some MPUs blur the line: the RZ/A2M in Module 2 has 4 MB of on-chip SRAM and runs an RTOS with no external DRAM.

- **Non-volatile memory (flash, EEPROM)** stores the **program code (firmware)**. It keeps its data with the power off and can be rewritten for **firmware updates**.
- **Volatile memory (SRAM)** holds the **runtime data**, such as variables, and loses it at power-off. It has two key regions:
  - the **stack**, which handles function calls and local variables **automatically** in **LIFO** (last in, first out) order
  - the **heap**, which supplies memory the program asks for at runtime, for example with `malloc()`.
- At startup, the startup code copies the initial values of global variables from flash into SRAM.

> [!warning] Stack and heap in practice
> Many embedded projects **avoid or limit the heap**, because repeated `malloc()` and `free()` calls fragment the small RAM and take unpredictable time. A **stack overflow**, where the stack grows into other data, is a classic embedded crash, so size the stack carefully.

- **Inputs (senses)** let the system perceive its environment.
  - **Sensors** convert physical quantities such as temperature, light and motion into electrical signals.
  - An **ADC (analog-to-digital converter)** turns the analog sensor signal into numbers the processor can use.
- **Outputs (muscles)** let the system act on its environment.
  - A **DAC (digital-to-analog converter)** turns the processor's digital values into analog control signals.
  - **Actuators** turn electrical signals into physical action, such as a motor turning or a valve opening.
  - **Feedback** alerts the user by sight (LEDs, a display), sound (a speaker, an alarm) or touch (vibration).
- **Communication** is the mouth and ears:
  - **on-board**, between chips on the same board: **UART, I2C, SPI**
  - **network**: Ethernet, Wi-Fi, Bluetooth
  - **domain-specific**: **CAN bus** in cars, **Modbus** in industry.

## 0.5 Case Studies
> [!tip] Constraints shape the design
> Both products use the same building blocks: processor, sensors, outputs, communication and software. Their **constraints** lead to completely different designs.

| | Smart thermostat | Automotive ADAS camera |
|---|---|---|
| **Function** | Controls the home HVAC, with remote control and schedules over the internet | The car's "eyes" for **automatic emergency braking (AEB)** and **lane keeping assist (LKA)** |
| **Constraints** | Low cost, low power, always-on connectivity | Extreme performance, uncompromising safety and reliability (**ISO 26262**) |
| **Processor** | Low-power **MCU** (Renesas RA) | High-performance **SoC with AI accelerators** (Renesas R-Car) |
| **Inputs** | Temperature and humidity sensor over **I2C**, motion sensor | High-resolution automotive image sensor |
| **Outputs** | Relay that switches the HVAC, small OLED or LCD | High-priority commands such as "brake" to other ECUs |
| **Communication** | Wi-Fi and/or Bluetooth Low Energy (BLE) | Deterministic vehicle networks: CAN, automotive Ethernet |
| **OS** | Lightweight RTOS (FreeRTOS, Zephyr) to run tasks side by side | Certified RTOS or hypervisor (QNX) |
| **Application** | Control logic, UI, cloud messaging over **MQTT** | Perception stack (computer vision, AI models) and decision logic, built to **AUTOSAR** |

- **HVAC** is heating, ventilation and air conditioning.
- **MQTT** is a lightweight publish/subscribe messaging protocol made for IoT devices.
- **ISO 26262** is the functional safety standard for road vehicles. **AUTOSAR** is the standard software architecture for car ECUs.
- A **hypervisor** runs several operating systems isolated from each other on one chip, such as a safety RTOS next to infotainment software.

- **Layer 1, firmware and HAL (hardware abstraction layer):**
  - **Device drivers** control specific hardware parts.
  - The **bootloader** is the first code you write that runs. It initializes the hardware and loads the application.
- **Layer 2, RTOS:** manages the **tasks and their scheduling**, for example FreeRTOS or Zephyr. Simple devices often skip it and run **bare-metal** in a single main loop.
- **Layer 3, middleware:** common services such as networking stacks, file systems and graphics.
- **Layer 4, application:** the logic that makes this product what it is.

> [!tip] Why layers
> Each layer only talks to the one below it. Move to a new chip and you mainly rewrite the **drivers and HAL**, and keep the RTOS, middleware and application.

## 0.8 Future Trends
### 0.8.1 Edge AI
- **Edge AI** runs AI and machine learning models **on the device itself**, not in the cloud.
- It's enabled by power-efficient processors with built-in AI accelerators, called **NPUs (neural processing units)**.
- Its benefits:
  - **Low latency:** real-time decisions with no cloud round trip, which is critical for autonomous systems.
  - **Privacy and security:** sensitive data such as camera footage never leaves the device.
  - **Reliability:** it works without an internet connection.
  - **Cost savings:** less bandwidth and less cloud processing to pay for.

### 0.8.2 Security
- With **billions of connected IoT devices**, the attack surface has grown enormously.
- Embedded devices face unique problems:
  - an attacker may have **physical access** to the device
  - **long lifecycles** make patching difficult
  - **limited resources** can't run traditional security software.

**Security by design** builds protection in from the start:
- **Secure boot** creates a **chain of trust** from power-on and verifies that the firmware is authentic and untampered.
- A **Trusted Execution Environment (TEE)**, such as **Arm TrustZone**, is a hardware-isolated zone that protects sensitive code and data.
- **Memory protection** uses hardware to stop tasks from corrupting each other's memory.
- **Secure coding** avoids common bugs such as **buffer overflows**.

> [!abstract] Wrap-up
> Embedded systems are **dedicated, purpose-built computers** that form the backbone of modern technology. They're defined by their **constraints and specialization**, not their power, and **the application's requirements always dictate the architecture**.
